Tie Security Landscape

Where Tie's trust boundaries are, what crossed them, what was closed in this pass, and what stays open because the product wants it that way.

At a glance

Tie's design is sound: content never shares a JS realm with the shell, the shell session has no network, every guard has a scenario. The problems found were in the seams: one real bypass of the gesture rule, memory exhaustion through the content protocol, three Electron defaults nobody had turned off, and files on disk readable by other accounts.

Severity below is judged against Tie's own threat model: the attacker is a document, a page or a process you deliberately opened in a tile, and the prize is code running as you outside that tile.

Trust model

The one-line threat model from docs/SECURITY.md still holds and was the yardstick for everything below: viewing is safe, running is a choice, content never reaches the shell. Two consequences matter for reading the findings:

  • "As you" is the ceiling. Anything a local process of your account can already do is not a Tie vulnerability. It becomes one when a weaker party (a document, a site, a sandboxed agent) gets there through Tie.
  • Exits are the whole game. A page inside a frame can read what Tie hands it and compute on it. Damage needs an exit: the network (closed), the system browser (confirm), the shell (closed), your keyboard (closed in this pass), files on disk (downloads, gated now).

Fixed in this pass

Each item: where it was, who could use it, how, what they got, and what closed it. All are covered by a scenario or unit test unless noted.

fixed · high

A page could focus itself and pass the gesture rule

Where
renderer/frame.ts gesture rule (document.activeElement === frame); every content iframe.
Threat model
Any html file opened in a tile (a report an agent wrote, a vendored demo, a file from a repo). Also any future XSS in a viewer.
How
A cross-origin iframe may call window.focus() or el.focus() at any time. Chromium made the frame the shell's active element. The rule treating "focused" as "the user clicked here" then passed. Verified: a page's load script opened the external-link dialog with no click at all, and took focus back from a terminal after the user had moved there.
What it achieved
  • Keyboard theft: keystrokes meant for a terminal (a password at a sudo prompt) land in the page.
  • Gesture verbs without a gesture: open any local file beside the tile (one per second), raise the "Open in browser?" dialog at a moment of the page's choosing.
  • The page's tile became the active tile (⌘W, ⌘D then act on it).
Why it was there
The rule copied VS Code's, which lives inside a trusted webview preload. Tie's html pages are untrusted and cross-origin: the signal was never theirs to keep honest.

Blink refuses focus calls from a frame without transient user activation when the frame's permissions policy denies focus-without-user-activation. Every content iframe now carries allow="focus-without-user-activation 'none'" and main enables the BlockingFocusWithoutUserActivation feature. The page's own timers fail with "Blocked focus call…" in its console; a real click still focuses it. Browser guests never could move the shell's focus (verified). Scenario sec-focus (red first, and red if the feature is removed).

Discarded on the way: a shell-side guard fed by main's input-event. Main only observes input to the main frame; clicks routed into out-of-process frames never reach it, so that guard rejected real clicks. Documented in TILES.md so nobody rebuilds it.

fixed · medium

Any file in a tile's folder was read whole into main

Where
main/content.ts serveContent: readFile(real) for every root file, no size check.
Threat model
A markdown file with ![](big.iso), an html page fetching a sibling file, or just a legitimate 4 GB video next to a page.
How
The kind's size cap applied only to the document the tile opened. Everything the page or viewer referenced inside the root was buffered entirely in the main process.
What it achieved
Main-process memory exhaustion from a frame: freeze or crash of all of Tie, terminals included. The watchdog can't help; it only kills frames.

Root files are streamed (createReadStream → web stream response, Content-Length set). Html documents fetched from the root are still read whole for bootstrap injection, but refused above the kind's cap (10 MB). sec-html: a 10 MB + 1 document gets 404, a 12 MB asset arrives intact.

fixed · medium

Web Bluetooth picked the first device by itself

Where
Browser guests (and, in principle, any webContents). Electron's select-bluetooth-device default.
Threat model
A web site in a browser tile, after one click.
How
navigator.bluetooth.requestDevice({acceptAllDevices: true}) needs a user gesture. Without a handler, Electron answers the chooser with the first device found. The device-permission handler Tie sets covers USB, HID and serial, not this chooser.
What it achieved
A GATT connection to whatever BLE device is nearest (headphones, a lock, a sensor), with no prompt.

noDeviceChoosers: the event is prevented and answered with an empty id, logged, on guests and the shell window. Not testable in the harness (no device); covered by review.

fixed · medium

Client certificates were sent without asking

Where
app.on('select-client-certificate'): absent. Electron's default uses the first certificate in the keychain.
Threat model
Any https site in a browser tile that requests a client certificate.
What it achieved
Your corporate or personal identity certificate presented to an arbitrary site, silently.

Prevented, continued without a certificate, logged. Consequence to know: sites that need a client certificate don't work in browser tiles for now. A chooser can come later.

fixed · medium

Sites could save files into ~/Downloads with no interaction

Where
main/guest.ts will-download: sanitized name, no dialog, never opened, and no gesture check.
Threat model
Any site, including through an ad or a compromised dependency, with the tile merely open.
How
location = '/file' with Content-Disposition: attachment, in a loop if it likes.
What it achieved
Planted files: invoice.pdf.command, a poisoned .terminal, hundreds of junk files. Nothing runs by itself, but the next thing you double-click in Downloads might.

A download is saved only within 10 s of real input (mouse button or key) in that guest, the same signal the popup rule uses; otherwise blocked and logged. sec-browser: a page whose script starts a download with no input saves nothing. Residual: see "Open by design".

fixed · high on shared Macs

State dir, socket, logs and settings readable by other accounts

Where
~/.config/tie created 0755; sockets 0755 (umask); logs and settings 0644.
Threat model
Another local account on the same Mac (family, shared workstation, a guest account). macOS leaves ~ traversable and ~/.config is usually 0755.
How
Connect to ~salezica/.config/tie/default.sock and send open with --cmd. Or just read the logs: every tie call with its arguments, paths of files opened, URLs sent to the browser.
What it achieved
Command execution as you from another account; disclosure of what you work on.

The state dir and log dir are 0700, every file Tie writes there is 0600, the socket is chmod'ed right after listen, and existing files are fixed up at start. Socket request lines are capped at 1 MB (an unbounded buffer before). sec-state checks modes and the cap.

fixed · low

"Open in browser?" could be accepted by a click already in flight

Where
dialog.ts confirmDialog, used by html tiles for web links.
How
A page tracks the pointer, shows a lure button, and raises the dialog as you press. The Open button appears under your finger.
What it achieved
A URL of the page's choosing in your system browser, carrying whatever the page read from its folder in the query string.

Open is disabled for 600 ms after the dialog appears (Firefox's security delay). The dialog also shows the site address in bold and flags links with more than 200 characters after the origin as data the page may be sending. sec-focus.

fixed · low

Message floods from a frame

Where
frame.ts onRequest: every port message parsed and logged.
What it achieved
A tight postMessage loop in a page janks the shell UI and bloats the log when debugging is on.

More than 1000 messages a second from one frame are dropped before parsing.

Open by design

These follow from things Tie wants to do. Each says why the obvious fix isn't one, and what the realistic options are. They are the decisions left for you.

kept · design

The socket is full power for any process that can reach it

Where
main/socket.ts, bin/tie; TIE_SOCKET exported into every Tie shell.
Threat model
Not another account (fixed above). A process of yours that you meant to confine: an agent run under a sandbox, a tool with restricted file access, a container that mounts the socket dir.
How
The socket path is in the environment. One JSON line: open with kind: terminal and cmd. Unix sockets pass through most file-permission sandboxes if the directory is reachable.
What it achieves
Escape from any sandbox that doesn't block that socket: an arbitrary shell command as you, in a visible tile.
Why not fixed away
The whole point of tie is that shells and agents inside Tie drive it. An authorization layer means tokens per tile, scoped capabilities (open files yes, run commands no), and a UI to grant them. That is a feature, not a patch.
Options
  • Minimal: a setting that refuses --cmd from the socket (agents can still open files, URLs, terminals with a plain shell).
  • Per-tile tokens in TIE_SOCKET's neighbour TIE_TOKEN: a call may act only on tiles the caller's tile opened.
  • Document it where sandboxes are set up: exclude ~/.config/tie from the sandbox's reachable paths.
kept · design

An html page reads its whole folder, recursively

Where
main/content.ts: root = the page's directory; contentFile allows any depth below it.
Threat model
You open ~/report.html, or index.html at a repo root that holds .env, .git, keys. The page includes a bundled library that was compromised upstream, or was written by an agent you don't fully trust.
How
fetch('.ssh/id_ed25519') works (same origin, inside the root). The page can't send it anywhere: no network, no storage on disk, no shell. Its only exit is a link you open: "View full report online" pointing at https://host/?d=….
What it achieves
Exfiltration of anything under the folder, gated on one click of yours on a dialog that now shows the host in bold and warns about the long tail.
Why not fixed away
Pages need their folder: scripts, styles, data files, images. Narrowing the root breaks the feature; refusing dotfiles breaks .well-known-style setups and still leaves config.json. The file input (<input type=file>) is the same story: standard browser behaviour, your choice per file.
Options
  • Warn (or refuse) when the root is ~, / or a volume root. Cheap, catches the worst case.
  • Root = nearest folder with a marker (index.html beside the page, or a .tie-root), capped at the repo root.
  • Show the root in the tile's nav bar so the grant is visible while the page is open.
kept · design

Gesture rule means "focused", not "just clicked"

Where
frame.ts needsGesture verbs: followLink, openLink.
How
After you click into an html page, its scripts may post gesture verbs until focus leaves, and may refocus the frame within Chromium's transient activation window (a few seconds after your last click or key there).
What it achieves
While you work in the page: the external-link dialog at any moment (one at a time, Open disabled at first), local files opened beside (one per second), its tile's title changed.
Why not fixed away
Main can't see input routed into out-of-process frames (shown in this pass), so the shell has no trusted "a click just happened in frame X" signal. The viewers could report clicks, but for html pages the reporter is the page itself. Chromium's own activation state isn't exposed to the embedder for subframes.
Options
Accept (the exits are already gated); or move html pages to their own <webview> with a trusted preload that reports real clicks, at the cost of the lighter iframe model.
kept · design

Downloads: after one click, a site may save many files

Where
core/guest.ts downloadVerdict: 10 s window after real input.
What it achieves
Up to ten seconds of silent saves after any click, sanitized names, never opened.
Why not fixed away
You decided no download dialog. Chrome's answer is a prompt for repeated automatic downloads; that is a dialog.
Options
One download per input event; a per-site counter; or a non-modal "saved X" toast in the planned alerts system, so at least it is visible.
kept · pending

Packaged Tie runs as a generic Node binary

Where
Fuse runAsNode on; resources/bin/tie sets ELECTRON_RUN_AS_NODE=1.
Threat model
Malware already on the machine looking for a signed, trusted binary to live in (the Wave CVE-2025-12843 class). Not reachable from tiles.
Why not fixed away
The CLI launcher depends on it. Already in PENDING.md: a Tie --cli mode in main, then the fuse off. Unchanged here; it needs the packaging work.
kept · dev only

Dev builds listen on a CDP port

Where
main/index.ts: remote-debugging-port when not packaged (port derived from the instance name).
Threat model
Any local process while a dev instance runs (which, in practice, is most of the day). Localhost only, but a sandboxed agent that can open TCP connections can drive the shell, and the shell has window.tie.
Why not fixed away
The harness is built on it. Dev builds are not the product.
Options
Only open the port when TIE_DEBUG_PORT is set by tie-dev; a plain tie-dev run for daily use could leave it closed.
kept · design

Titles and icons are impersonable text

Where
Html <title>, terminal OSC titles, tie title / tie icon from any process.
What it achieves
A tile that looks like "Settings" or "~/.ssh" or a terminal that looks like another one. Nothing runs; it steers the user. Bounded, control characters stripped, always text.
Why not fixed away
Titles are the feature. A kind glyph that content can't set (already the case for the automatic icon) is the honest signal; keep it visible.
kept · design

Browser tiles are one shared, persistent profile with full network

Where
persist:browser for every browser tile.
What it achieves
What any browser allows between sites in one profile: cookies shared across tiles, plain http allowed, tracking across sessions. Tie adds nothing on top (no sync, no extensions, no Tie schemes reachable).
Why not fixed away
Logins surviving restarts was the decision. Per-tile or private profiles are in PENDING.md.

Method

  • Read: all of src/main, src/core, the preload, the frame host, file view, html and browser kinds, the viewer runtime and bootstrap, markdown/text/image viewers, shell CSP, packaging fuses, the CLI launcher, and every sec-* scenario's shape. Markup sinks grepped across the renderer: all text goes through textContent, icons escaped.
  • Probed: focus stealing from html frames and browser guests (real finding); whether main's input-event sees CDP and routed-frame input (it does not); Blink's focus policy with page-timer scripts (works); Electron 44 source for where input observers attach (main frame only).
  • Checked against Electron's defaults: permission handlers (already denied), device permission handler (set), Bluetooth chooser (was default), client certificates (was default), login (default cancels), downloads (was ungated).
  • Did not find: traversal in either protocol handler (decode once, reject leftovers, realpath, containment), IPC from anything but the shell's main frame, a way for content to reach window.tie or another tile's token, a network path from the shell session, a scheme other than http(s) reaching the OS.
