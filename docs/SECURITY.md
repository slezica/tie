# Security

Onboarding explainer (processes, realms, doors per tile, layers, threats, stories): `docs/EXECUTION-AND-SECURITY.html`.

## Threat model

- UI renderer holds `window.tie` (spawns ptys): any script there = RCE as the user.
- Content frame roots (`DIRECTORIES.md` 5–7): a document can show files under its root (the context tile's cwd, often a project; `~` when opened from there: the user's choice, record 2026-11-13). Display inside the sandbox only: no network, no scripts, no other tile. Root `/` asks first.
- Untrusted input: terminal output (OSC 8 links, titles), pasted and dropped data (incl. file names), content tiles (markdown, text, image, hex, html): any script inside their frame; browser tiles: any web site (its own webContents, `BROWSER.md`). Html pages are static (decision 2026-10-21: their scripts never run; only Tie's bootstrap does, by nonce); still local (no network) and isolated (own origin, no UI access, no other tile).
- Picker walks (`doc:walk`): the UI realm is trusted, so a compromised UI could list (names only) any directory the user can read; it could already do worse (`window.tie` spawns ptys). Still bounded: absolute, normalized, existing directories only; directory symlinks never followed; protected (TCC) roots listed, never entered unless the walk is rooted there; 50k entries / 2 s; one walk per window.
- The `tie` socket: reachable only by the user's own processes, which can already run code. Kept to them: the state dir is 0700 and the socket 0600 (other local accounts never reach it). Whoever is let in has the user's full power (`tie add terminal --cmd`). Callers are identified by the kernel (peer pid + uid, then process lineage): one running in a Tie terminal acts as that tile (`TIE_TILE` is not trusted); others (scripts, other apps, sandboxed agents inheriting `TIE_SOCKET` outside Tie) only with `allowExternalControl` (default off). Not a boundary between processes in the same terminal.
- The state dir is trusted as the user's own: settings, sockets, UI state, a staged update there carry the user's trust (anything that can write there already runs as the user). The UI state file is still parsed as untrusted (`parseUiState`): it holds only numbers, clamped.

## Rules

- Only our code runs in the UI. Content never shares its JS realm.
- Every guard gets an e2e scenario, written red first (`sec-*` when the scenario is the guard's own). Guards get lost in refactors otherwise. No scenario, or a guard no harness path reaches: said in its row.
- Security-relevant code carries a `// SECURITY:` comment saying what matters about it.
- New IPC: `ipc.on` / `ipc.handle` (`uiIpc`), never `ipcMain` directly.
- Opening URLs: only `openExternal` in `src/main/security.ts`. This rule and the previous one: unit-checked (`core/docs.test.ts`), as is every scenario named below.
- Pure checks, unit-tested: `src/core/security.ts`, `content.ts`, `callers.ts`, `keymap.ts` `decideKey` (main), `guest.ts`, `log.ts`, `settings.ts`, `barsize.ts` (UI state payload / file), `paste.ts`, `requests.ts`, `links.ts`, `kinds.ts`, `roots.ts`.
- Content kinds only through the frame host (`TILES.md`): the baseline is not per kind. What differs per kind (page, sandbox, CSP, nav rule, assets, payload, size cap, bootstrap) lives in one table: `src/core/policy.ts` (`TILES.md` "Policy table"), every row pinned by `policy.test.ts`.
- Never add `tie-content:` to the UI's `script-src`; never post to frames by name or `'*'` except the handshake to the exact `contentWindow`.
- `allow-same-origin`: document kinds only (html), on their own `tie-content://<token>` origin, never the UI's (a same-origin frame could lift its sandbox). Viewer kinds: opaque.
- The UI window runs on an in-memory session (`UI_PARTITION`): content storage never reaches disk. It has no network (`noNetwork`): Tie's pages are all custom-scheme (dev `--hot`: the dev server's host:port exempt). The browser kind has its own partition (`persist:browser`, network, none of Tie's protocols).
- Browser guests: only through `attachGuest` (prefs rebuilt, attributes dropped) and `guardGuest`; URL rules only in `core/guest.ts`. Mechanisms: `BROWSER.md`.
- Terminal children are their own TCC responsible process (disclaimed spawn, `TERMINALS.md` "Spawn"): what runs in a terminal never prompts as Tie, and permissions granted to Tie (none needed) never extend to it.

- On: `runAsNode` (CLI launcher needs it), cookie encryption, asar integrity, only-load-from-asar.

## Harness

- `probe(ctx)`: local http page reporting hits and whether it got `window.tie`. `assertUntouched(what)`. In UI-session scenarios the dead proxy covers loopback: a probe hit can't happen, so `assertUntouched` re-checks `noNetwork` only; each case asserts its guard's own signal (`[security]` log line, CSP violation).
- Probe kind (dev builds): `tie add probe [--root D]`, `h.contentFrame(ctx, id)` = Playwright frame inside it (the attacker's seat). `h.frames(ctx)` / `tie-dev frames`: frame tree, out-of-process.
- `ctx.appLog()`: run's app log as a human reads it (`<untrusted>` markers removed, escapes undone); `ctx.rawLog()`: the file. `[security]` lines record every block/refusal and are written even with `TIE_DEBUG` unset (`sec-log`). Values that aren't Tie's (URLs, hrefs, paths, names, request bodies, socket params) are logged as `<untrusted>…</untrusted>`, escaped (`core/log.ts` `untrusted`): wrap them at the call site.
- Socket: the harness is an external caller. `launch()` seeds `allowExternalControl: true` (scenarios override it with `export const settings`).
- Harness instances (`TIE_BACKGROUND`) log `external open <url>` instead of opening, and never show the native file dialog (dev socket `pick` answers it; Tie's picker is HTML, driven like any dialog).
- Markdown: `h.contentFrame(ctx, id)` = the viewer's frame; `window.markdown.port` lets a scenario post requests as the frame (write-shaped messages, gesture-less links).
- Keys: `h.press` / `keyDown` / `keyUp` go through main (`sendInputEvent`); CDP keys skip `before-input-event`. Main's key mode: dev socket `key-mode` (read-only), `h.waitKeyMode`. Playwright's `evaluate` runs with a user gesture (CDP `userGesture`): it can't show what a page's own script may do without one (focus, popups); use the page's own timers for that (`sec-focus`).
- Limits: no harness path sends a key that is both routed into a focused frame and seen by `before-input-event`: `h.press` keys (`sendInputEvent` on the window) reach the shell document even with a frame focused. `sec-keys` focuses the frame for real (`hiddenWindow`) and checks main's block in the shell page, with a positive control (a plain key arrives there). Real-hardware check: manual.
- Limits: offscreen + CDP can't reach the native navigate-on-drop path; `sec-drop` asserts the mechanism (drags claimed).
- Browser: `h.guestPage` = the guest's realm (what a site can do); `h.guestKey` / `h.guestClick` = input through main (gesture + shortcuts); dev socket `guest` (`list`, `crash`, `key`, `click`, `proxy`). Downloads go to `TIE_DOWNLOADS` (dev builds; every harness instance), never `~/Downloads`.
- Html: `h.htmlFrame(ctx, id)` = the page's realm (what a renderer bug would get: page scripts never run); `tie list --json` `page`. CSP violations observed in the page (`securitypolicyviolation`), so the CSP layer is tested even though the network kill-switch would also stop requests.
