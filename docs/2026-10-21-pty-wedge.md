# macOS pty wedge

Symptom (installed Tie 0.2.0, twice in one day): new terminal tiles never start; the title shows the shell path, the body stays empty. New tabs, other shells, even `htop` as the shell: same.

# Diagnosis

- Every `spawn-helper` (node-pty) of the app is stuck in state `U` (uninterruptible), `sample` shows `main → ttyname → ttyname_r → devname_r → lstat`: the `lstat("/dev/ttysNNN")` never returns. Unkillable.
- Not Tie: a plain `python3 -c 'pty.openpty()'` hangs the same way; `ps aux` and `lsof` hang too (they stat ttys). ~130 helpers stuck across the installed app and every harness instance, plus three `nvim` (one wedged on resume after ctrl-z, in `uv_tty_init → ttyname_r → lstat`).
- Not exhaustion: 264 live `/dev/ttys*` of `kern.tty.ptmx_max` 511, and exhaustion gives `ENXIO`, not a hang.
- Timeline: last known-good pty spawn 19:10 (an e2e run), first stuck process before 22:07 (nvim), installed Tie's first stuck helper 22:11; no harness activity 19:10–22:13, so the harness didn't trigger it. The trigger is unknown.
- Prior art: node-pty master leaks on macOS 26 (Claude Desktop, Cursor) exhaust ptys and fail with errors; no report of a devfs `lstat` hang.
- Only a reboot clears it. Kernel stacks would need `sudo spindump -notarget 3 -file ...` before rebooting.

# Harness

- `tie-dev ptys`: live count, and spawn-helpers stuck in `U` (= the wedge).
- `drive` records the pty delta of each scenario (`ptys=N` in `drive.log`); `test --e2e` flags `(ptys +N)`. After the reboot: baseline 18, full suite 0 leaked.
- `tie-dev ptydump`: snapshot for the next occurrence (stuck processes + stacks, probes, sleep/wake + kernel logs, Tie state); then the printed `sudo spindump` for kernel stacks. `HARNESS.md`.
